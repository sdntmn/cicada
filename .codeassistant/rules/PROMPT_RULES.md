# Правила проекта для AI-ассистента

## Архитектура FSD (Feature-Sliced Design)

Проект использует Feature-Sliced Design со следующими слоями:

### Слои (от низкого к высокому уровню):

1. **`shared/`** - переиспользуемый код, не зависящий от бизнес-логики
   - `ui/` - UI-компоненты (Button, Input, Table и т.д.)
   - `lib/` - утилиты, хуки, helpers
   - `api/` - API-клиенты, конфигурация запросов
   - `config/` - конфигурационные файлы
   - `types/` - общие типы TypeScript

2. **`entities/`** - бизнес-сущности (User, Debtor, Premises и т.д.)
   - `model/` - логика сущности (slice, thunk, types, services)
   - `ui/` - компоненты, специфичные для сущности
   - `lib/` - утилиты для сущности

3. **`features/`** - пользовательские сценарии (фичи)
   - `ChangeDebtStage/`, `GlobalSearch/`, `HouseMultiSelect/` и т.д.
   - Каждая фича содержит свою логику и UI

4. **`widgets/`** - композитные блоки из нескольких фич/сущностей
   - `BaseTable/`, `Notifications/`, `TopNav/`, `SubNav/`

5. **`pages/`** - полноценные страницы приложения
   - `Dashboard/`, `Debtors/`, `Court/`, `PreparationClaim/` и т.д.
   - Собирают фичи, виджеты и сущности в законченные страницы

6. **`app/`** - настройка приложения
   - `providers/` - провайдеры (StoreProvider и т.д.)
   - `styles/` - глобальные стили, темы
   - `lib/` - прикладные утилиты

### Правила импортов:

- Использовать абсолютные импорты через алиас `@` (настроен в `tsconfig.json`)
- Пример: `import { Button } from "@/shared/ui/Button"`
- Запрещены относительные импорты с большим количеством `../`
- Импорты между слоями только снизу вверх (shared → entities → features → widgets → pages → app)

## Правила ESLint

### Ключевые правила:

#### Сортировка (perfectionist плагин):

- **Импорты сортируются алфавитно** по группам: react, external, common, internal-src, parent, sibling, internal, index
- **JSX пропсы сортируются алфавитно** (кроме multiline, unknown, shorthand групп)
- **Объекты, интерфейсы, enum'ы сортируются алфавитно**
- **Именованные импорты сортируются алфавитно**

#### Форматирование (Prettier):

- **Отступы**: 2 пробела
- **Кавычки**: двойные для JSX, одинарные для JavaScript
- **Точка с запятой**: не использовать
- **Запятая в конце**: для многострочных структур
- **Максимальная длина строки**: 135 символов

#### React правила:

- **JSX boolean атрибуты**: явно указывать значение (`isActive={true}`)
- **Ключи для списков**: обязательны (`key`)
- **Self-closing компоненты**: для компонентов без детей
- **Порядок атрибутов в JSX**:
  1. `className`
  2. `id`
  3. `aria-*` атрибуты
  4. `data-*` атрибуты
  5. Обработчики событий (`onClick`, `onChange`)
  6. `ref`
  7. Остальные пропсы

#### TypeScript правила:

- **Типы массивов**: использовать `Type[]` вместо `Array<Type>`
- **Запрет `any`**: отключен (но стараться избегать)
- **Запрет non-null assertion**: ошибка (`!`)
- **Consistent type assertions**: использовать `as Type`

#### Общие правила:

- **`no-console`**: разрешены только определенные методы (`log`, `info`, `warn`, `error`, etc.)
- **`prefer-const`**: использовать `const` для неизменяемых переменных
- **`eqeqeq`**: строгое равенство (`===`, `!==`)
- **`no-var`**: использовать `let`/`const` вместо `var`
- **`curly`**: всегда использовать фигурные скобки для блоков

## Правила Stylelint (SCSS)

### Основные правила:

- **Цвета в HEX**: использовать длинный формат (`#ffffff` вместо `#fff`)
- **Нулевые значения**: без единиц измерения (`0` вместо `0px`)
- **Порядок свойств**: с помощью `stylelint-order`
- **Вендорные префиксы**: запрещены вручную (использовать autoprefixer)

### SCSS-специфичные:

- **Миксины**: использовать `@mixin` и `@include`
- **Вложенность**: максимальная глубина - 4 уровня
- **Именование классов**: БЭМ-нотация с модификаторами через `__` и `--`
- **Переменные**: использовать CSS-переменные из тем (`var(--color-text-primary)`)

## Правила именования

### Файлы:

- **Компоненты React**: `PascalCase.tsx` (например, `Label.tsx`)
- **Стили**: `kebab-case.scss` (например, `styles.scss`)
- **Хуки**: `useCamelCase.ts` (например, `usePagination.ts`)
- **Утилиты**: `camelCase.ts` (например, `formatDate.ts`)

### Переменные и функции:

- **Компоненты**: `PascalCase`
- **Функции/хуки**: `camelCase`
- **Константы**: `UPPER_SNAKE_CASE`
- **Типы/интерфейсы**: `PascalCase` с префиксом, если нужно (`Props`, `State`, `Type`)

## Структура компонента UI

Пример правильной структуры компонента в `shared/ui/`:

```
ComponentName/
├── index.ts              # публичный API (экспорт типов и компонента)
├── ui/
│   ├── ComponentName.tsx # основной компонент
│   └── styles.scss      # стили компонента
└── lib/                  # (опционально) утилиты для компонента
```

### Требования к компоненту:

1. Использовать `forwardRef` для компонентов, которые должны получать ref
2. Определять `displayName` для отладки
3. Использовать `classnames` для условных классов
4. Поддерживать `className` и `style` пропсы
5. Использовать TypeScript типы для пропсов
6. Экспортировать типы пропсов отдельно
7. **Именование пропсов**: использовать просто `Props` вместо `ComponentNameProps` (например `interface Props`, а не `interface CardProps`)
8. **Экспорт пропсов**: не экспортировать типы пропсов через `index.ts` - они должны быть доступны только через импорт из файла компонента

## Работа с состоянием (Redux Toolkit)

### Структура slice:

```typescript
// model/slice/exampleSlice.ts
export interface ExampleState {
  data: Type[]
  isLoading: boolean
  error: string | null
}

export const exampleSlice = createSlice({
  name: "example",
  initialState,
  reducers: {
    /* ... */
  },
  extraReducers: (builder) => {
    /* ... */
  },
})
```

### Асинхронные операции:

- Использовать `createAsyncThunk`
- Обрабатывать состояния `pending/fulfilled/rejected` в `extraReducers`
- Использовать утилиты `isPending/isFulfilled/isRejected` из `@reduxjs/toolkit`

## Тестирование

### Приоритеты:

1. **Компоненты**: тестировать рендеринг и пользовательские взаимодействия
2. **Утилиты**: unit-тесты для pure-функций
3. **Слайсы**: тестирование редьюсеров и экшенов
4. **Селекторы**: тестирование мемоизированных селекторов

## Коммиты и Git

### Conventional Commits:

- `feat:` - новая функциональность
- `fix:` - исправление бага
- `docs:` - изменения в документации
- `style:` - форматирование, отсутствие изменений в коде
- `refactor:` - рефакторинг кода
- `test:` - добавление или исправление тестов
- `chore:` - обновление зависимостей, настройка инструментов

## Быстрые команды для проверки

```bash

npx tsc --noEmit --skipLibCheck

# Проверка ESLint
npx eslint src/ --ext .ts,.tsx

# Проверка Stylelint
npx stylelint "src/**/*.scss"

# Форматирование Prettier
npx prettier --check "src/**/*.{ts,tsx,scss}"
```

## Примечания для AI-ассистента

1. **Всегда проверяй код на соответствие этим правилам** перед созданием или изменением файлов
2. **Используй абсолютные импорты** через `@/`
3. **Следуй порядку атрибутов в JSX**
4. **Сортируй импорты** согласно конфигурации perfectionist
5. **Проверяй типы TypeScript** и избегай `any`
6. **Сохраняй архитектурную чистоту FSD** - не нарушай границы слоев
7. **Для UI-компонентов используй БЭМ-нотацию** в CSS-классах

Эта документация должна быть использована как справочник при выполнении любых задач в проекте.
